## Передумови, дані та критерії перевірки

- Кожен кейс незалежний: окремий браузерний контекст, власна підготовка стану. Попередній кейс не є передумовою наступного.
- **A0:** відкрити SauceDemo, авторизувати `standard_user` із дозволеними демонстраційними даними, відкрити `/inventory.html`; каталог завантажений, кошик порожній. Початкову порожнечу перевірити, за потреби видаливши наявні товари через UI. Пароль у документі не зберігається.
- **A1:** у власному A0 додати товар P через каталог; перевірити його наявність у кошику. **A2:** у власному A0 додати P і Q та перевірити склад кошика. Потім перейти на екран, указаний у кейсі.
- **P:** Sauce Labs Backpack; **Q:** Sauce Labs Bike Light. Це назви із AC, а не довільно вигадані дані.
- Перед додаванням записати назву, опис і ціну вибраного товару з каталогу/деталей. Це **критерій узгодженості між екранами**, а не незалежний еталон правильності ціни; питання Q-04 з аналізу залишається відкритим. Не фіксувати числові ціни або загальну кількість товарів із пам’яті.
- У перевірці складу кошика порівнювати точний набір вибраних товарів, а не тільки badge. Для P кількість 1 прямо задана AC-004; для інших товарів контролювати наявність поля кількості та відсутність дубльованих рядків за BR-001, не вигадувати правила редагування кількості.
- Пріоритет кейсу — запропонований ризик-орієнтований: Critical для основного додавання, High для цілісності/доступу, Medium для навігації та останнього видалення. Це не новий офіційний пріоритет BR/AC.
- **Ready** означає достатній критерій для описаної частини. **Partial** — виконувана частина є, але не покриває весь неоднозначний контракт. **Blocked** — немає відтворюваного тригера/критерію. **Proposed** — NFR ще не погоджено.

## Equivalence Partitioning та переходи станів

| Клас | Вимір | Представник | Кейси |
|---|---|---|---|
| EP-A1 | Авторизований користувач | standard_user | TC-CART-01–13 |
| EP-A2 | Неавторизований користувач | Новий контекст без сесії | TC-CART-14 |
| EP-C0 | Порожній кошик | Немає вибраних товарів | TC-CART-01, 02, 07, 08 |
| EP-C1 | Один товар | P | TC-CART-02, 07–13 |
| EP-C2 | Декілька різних товарів | P і Q | TC-CART-03, 04, 05, 06 |
| EP-P0 | Товар відсутній | P до першого add / після remove | TC-CART-01, 02, 05–08 |
| EP-P1 | Товар уже присутній | P у власному A1/A2 | TC-CART-04–07, 09–13; TC-CART-15 заблокований |
| EP-S1 | Додавання з каталогу | Add to cart для P | TC-CART-02, 03 |
| EP-S2 | Додавання з деталей | Add to cart на деталях P | TC-CART-08 |

Різні стани мають різні очікування, тому «товар уже є» не замінюється повторним кліком у координати Add: там уже може бути Remove. Повний декартів добуток класів не потрібен.

| Перехід | Цільова перевірка | Кейси |
|---|---|---|
| 0→1 | Точний товар, Remove, badge=1 | TC-CART-02, 08 |
| 1→2 | Два різні товари, badge=2 | TC-CART-03 |
| 2→1 | Видалено лише цільовий товар, badge=1 | TC-CART-05, 06 |
| 1→0 | Останній товар видалений, badge відсутній | TC-CART-07 |
| 1→1 під час переходів | Склад не змінюється | TC-CART-09–12 |

Нижня межа BVA: видалення останнього товару 1→0. Значення 2 тут представник класу «декілька», а не максимальна місткість. Верхня межа, кількість понад 1 для одного товару та часова межа приймання не визначені.

### TC-CART-03 — додавання двох різних товарів

### TC-CART-04 — відкриття кошика та дані кожного товару

Назви, описи й ціни відповідають записаним даним вибраних товарів; кількість P=1; для обох є поле кількості та Remove. - **Requirement ID:** FR-006, BR-001.
- **Статус / пріоритет / техніка:** Blocked, Q-02 / High / негативний сценарій, EP-P1.

## NFR-кандидати — поза основним приймальним набором

| Кандидат | Requirement ID | Запропонований дизайн після погодження | Що блокує приймальний pass/fail |
|---|---|---|---|
| CAND-NFR-01 | NFR-001 | На власному A0 виміряти інтервал від Add до оновлення кнопки й badge; порівняти з пропозицією ≤2 с | Не визначені нормальні умови, метод вимірювання, повтори й правило оцінки; 2 с не затверджений SLA |

## Відсутнє покриття та відкриті питання

1. **Q-02:** визначити дозволений повторний Add — потрібен для виконання TC-CART-15 та завершення FR-006/BR-001.
2. **Q-03:** уточнити Remove й синхронізацію кнопок на деталях; не зараховувати каталог як усі поверхні.
3. **Q-04:** погодити еталон даних або достатність міжекранної звірки для ціни/опису.
4. **Q-05:** визначити ознаки успішного переходу до checkout і поведінку порожнього кошика.
5. **Q-01/Q-06:** явно додати порожній початковий кошик до AC-001; визначити спосіб відмови для анонімного `/cart.html`, якщо потрібні exact assertions.
6. **Q-07:** reload, нові вкладки, Back/Forward, logout/login і завершення сесії не включені без правил збереження.
7. **Q-08/Q-09:** погодити NFR, власника вимог і перевірювані джерела замість `GitHub+2`.

Максимальна місткість, кількість понад 1, мережеві збої, видалення вже відсутнього товару, checkout-форма/оплата та спеціальні демоакаунти не мають достатніх вимог. Для них не створено вигаданих pass/fail-кейсів. Детальні питання та ризики наведено в [аналізі](shop-requirements-analysis.md).
