# Аналіз вимог Shopping Cart

Дата: 16 листопада 2026 року. Роль: `requirements_analyst`.
Джерело: [req/shop.txt](../req/shop.txt), версія 1.0, SauceDemo / Swag Labs.

## 1. Опис функціональності та статус джерела

**US-CART-001:** авторизований користувач додає товари до кошика для подальшого оформлення замовлення. Обсяг документа включає додавання з каталогу й деталей товару, перегляд, видалення, навігацію зі збереженням стану та перехід до checkout. Саме оформлення замовлення не описано.

Основні передумови джерела: `standard_user` авторизований, відкрито `/inventory.html`, перелік товарів доступний. BR-006 є окремим негативним сценарієм, для якого авторизована передумова навмисно не застосовується.

FR, BR та AC нижче — **заявлені вимоги наданого документа**, а не результати перевірки живого сайту. Формального погодження документа не наведено. NFR прямо позначено джерелом як запропоновані критерії навчального проєкту. Позначка `GitHub+2` не містить перевірюваних посилань і не підтверджує походження вимог. Сайт, зовнішні джерела й реалізація в цьому аналізі не перевірялися.

Статуси тестованості:

- **Ready:** очікування достатньо конкретне для дизайну кейсу в зазначеній області.
- **Partial:** інваріант визначено, але частину шляху, даних чи повноту перевірки треба уточнити.
- **Blocked:** завершений відтворюваний сценарій неможливо визначити без уточнення.

## 3. Бізнес-правила

У джерелі пріоритетів BR немає; їх не слід видавати за офіційно задані.

| ID | Правило | Зв’язки та межі перевірки |
|---|---|---|
| BR-001 | Один товар присутній лише один раз | FR-006; AC-004 задає кількість 1 для Backpack. Інваріант унікальності перевіряється у звичайних сценаріях, але це не повне покриття повторного add |
| BR-002 | Badge рахує різні товари | FR-004/005/007/011, AC-001/002/003. Можна перевірити переходи 0→1→2→1→0 без вигадування верхньої межі |
| BR-003 | Видалення не зачіпає інші товари | FR-007, AC-003; перевіряти збереження ідентичності й даних іншого товару |
| BR-004 | Кнопка відповідає наявності товару | FR-001/003/007. Після видалення Add to cart у каталозі прямо підтверджено AC-003; обсяг синхронізації деталей/каталогу потребує уточнення |
| BR-005 | Add не переводить автоматично до кошика | AC-001 явно залишає користувача в каталозі. Для деталей можна перевіряти відсутність автоматичного переходу в кошик, але не приписувати джерелу конкретний інший redirect |
| BR-006 | Анонімний прямий доступ до кошика заборонений | Ready для негативного інваріанта «захищений кошик недоступний» у чистому контексті. Конкретні redirect, HTTP status, текст помилки й механізм захисту не задані. Не підтверджено живою перевіркою |

| NFR-001 | Кнопка й badge оновлюються не довше 2 секунд за нормальних умов | Погодити критерій; визначити «нормальні умови», точку початку/кінця вимірювання, обладнання/мережу, кількість вимірювань і правило оцінки. Не видавати 2 секунди за підтверджений SLA |

| NFR-004 | Зрозумілі доступні назви, активація клавіатурою | Погодити критерії доступних назв, перелік кнопок, клавіші/фокус, середовище та очікуваний стандарт. Не додавати вимогу конкретного WCAG-рівня від себе |

## 6. Неоднозначності та питання

1. **Q-01, AC-001:** чи слід явно додати Given «кошик порожній»? Це запропоноване уточнення; поточний документ не гарантує початкової порожнечі всіх сценаріїв.
2. **Q-02, FR-006/BR-001:** яким дозволеним механізмом повторно додається вже вибраний товар, якщо кнопка стала Remove? Це повторний запит, інший екран, швидкі натискання чи інша дія? Другий клік у тому самому місці може бути Remove, тому не є коректним тестом повторного Add. Не вигадувати API endpoint або маніпуляцію storage як вимогу.
3. **Q-03, FR-007/BR-004:** які поверхні підтримують Remove — каталог, деталі, кошик? Як саме синхронізуються їхні кнопки після додавання/видалення? Для каталогу та наявності Remove у кошику є явні згадки; повний обсяг деталей не визначений.
4. **Q-04, FR-009/AC-004:** де зберігається еталон назв, описів і цін? Чи достатньо звірки з каталогом/деталями? Така звірка перевіряє перенесення даних, але не незалежну правильність ціни. Не закріплювати числові ціни з пам’яті або попередніх тестів.
5. **Q-05, FR-014:** який екран/маршрут підтверджує початок checkout? Чи доступний він із порожнім кошиком? Доступність кнопки не дорівнює повній перевірці переходу.
6. **Q-06, BR-006:** яка погоджена реакція на анонімний `/cart.html`? Можна вже перевіряти заборону доступу; точний URL, повідомлення й HTTP-код не визначені.
7. **Q-07, FR-010:** чи входять reload, Back/Forward, нова вкладка, logout/login або завершення сесії до збереження кошика? Вимога наразі описує лише переходи між трьома екранами.
8. **Q-08, NFR-001..004:** хто погоджує запропоновані критерії й уточнює вимірювані параметри? До погодження їх слід вести окремо від приймального набору.
9. **Q-09, джерело:** хто власник/погоджувач версії 1.0 та які посилання стоять за `GitHub+2`? Результат цього аналізу не підтверджує відповідність вимог живому SauceDemo.

## 7. Ризики та залежності

- **Хибне повне покриття FR-006:** перевірка одного рядка в кошику після звичайного додавання не доводить стійкість до повторної спроби.
- **Неізольовані дані:** непорожній кошик порушує очікування badge=1/2. Кожен кейс має власний визначений початковий стан; спосіб очищення не слід підміняти непогодженою прихованою API-операцією.
- **Слабкий критерій перевірки:** лише badge не доводить додавання правильного товару; лише видима ціна не доводить її коректності.
- **Невиправдане розширення обсягу:** checkout, кількість понад 1, гранична місткість кошика, network errors і довготривале збереження не мають заданих правил.
- **Змішування статусів:** NFR-пропозиції, записані FR/BR та live-факти мають різний статус. Не можна вважати запропонований SLA дефектом продукту без погодження.
- **Зовнішня залежність:** виконання залежатиме від доступності сайту, демонстраційного акаунта, товарів Backpack/Bike Light і стабільного тестового стану.
- **Безпекова межа:** UI-відмова для анонімного користувача не доводить захист усіх серверних ресурсів або API.

## 8. Запропонований обсяг та передача test_designer

**Ready:** початкові кнопки товарів; додавання одного й двох різних товарів; точність складу й badge; зміна кнопок; відкриття кошика; показ назви/опису/ціни/кількості; видалення й збереження іншого товару в явно обраній підтриманій поверхні; зникнення badge після останнього видалення; додавання з деталей; збереження під час навігації й Continue Shopping; доступність Checkout у непорожньому кошику; заборона анонімного прямого доступу без вигаданого redirect.

**Partial:** повне покриття FR-007/BR-004 для всіх поверхонь; FR-014 щодо конкретної цілі checkout; FR-009 щодо незалежного еталона ціни. У кейсах позначати покриту частину й залишкову прогалину, не ставити «повністю покрито».

**Blocked:** виконуваний сценарій повторного додавання FR-006 до відповіді Q-02. Інваріант BR-001 усе одно може перевірятися у звичайних кейсах. NFR-001..004 залишити окремими кандидатами до погодження, не включати до затвердженого pass/fail-набору.

Техніки для дизайну: класи еквівалентності «товар відсутній/присутній», «порожній/один/декілька різних товарів», «авторизований/анонімний»; переходи станів 0→1→2→1→0; нижня межа видалення останнього товару. Максимальна кількість товарів і межа часу для приймання не встановлені. Не потрібно створювати вигадану верхню BVA-межу або повний декартів добуток сценаріїв.

Код, вихідний документ і наявні тести не змінено. Цей документ є аналізом вимог, а не протоколом виконання тестів.
