# SauceDemo — тест-кейси авторизації

Дата дизайну: 16 листопада 2026 року. Авторська роль: `test_designer`.

## Основа та межі

Джерело очікувань — підтверджені дослідницькі результати `requirements_analyst` від 16.11.2026 для [SauceDemo](https://www.saucedemo.com/), наведені в поточній розмові. Попередній [план](saucedemo-auth.spec.md) від 12.10.2026 використано як контекст. Цей документ деталізує його сценарії та додає трасування; це не другий незалежний набір вимог.

**Окремої затвердженої продуктової специфікації немає.** AUTH-01–AUTH-10 — збережені аналітичні ID підтвердженої поведінки, а не офіційні вимоги продукту. Очікування не поширюються на неперевірені комбінації даних або середовища. Пріоритети запропоновані за ризиком: P0 — основний доступ, його заборона та вихід; P1 — валідація, зручність введення й збереження доступу після reload.

Нижче **13 спроєктованих кейсів: 4 позитивні, 8 негативних і 1 перевірка властивості поля**. Їх не виконували заново під час дизайну; підтвердження поведінки походить із попереднього дослідження. Код та існуючий план не змінюються. Покриття означає покриття дизайном, не автоматизацією чи виконанням.

## Спільні передумови та дані

- Кожен кейс починається в окремому чистому браузерному контексті без cookies, local/session storage та авторизованого `storageState`; не залежить від іншого кейсу.
- `LOGIN_URL` = `https://www.saucedemo.com/`; `INVENTORY_URL` = `https://www.saucedemo.com/inventory.html`.
- Передумова **L**: відкрити `LOGIN_URL`, переконатися, що поля `Username`, `Password` і кнопка `Login` видимі; поля порожні.
- Передумова **A**: у власному чистому контексті виконати L, ввести `standard_user` та `DEMO_PASSWORD`, натиснути `Login`; переконатися, що URL точно `INVENTORY_URL`, видно `Products` і список товарів, форма входу прихована. Це власна підготовка кейсу, а не залежність від TC-AUTH-01.
- `DEMO_PASSWORD` — опублікований на формі демонстраційний пароль; його значення в документі не дублюється.
- `WRONG_PASSWORD` — непорожній завідомо неправильний тестовий пароль, наприклад `wrong_password`; `UNKNOWN_USERNAME` — невідоме демонстраційному сервісу ім’я, представник `unknown_user` з попереднього плану. Перед виконанням переконатися, що тестові дані залишаються невірними.
- `EMPTY` — порожній рядок, не пробіли.
- Результат **S**: точний URL `INVENTORY_URL`, видно `Products` і список товарів, форма входу прихована.
- Результат **F**: точний URL `LOGIN_URL`, форма та кнопка `Login` видимі, список товарів не відображається. Для кожного негативного кейсу також обов’язкове його точне повідомлення.

## Equivalence Partitioning

Класи виділено за перевіреними властивостями та результатами. Один представник не доводить однакову поведінку всіх можливих рядків. Зокрема, звичайний валідний користувач не представляє спеціальні демоакаунти.

| Клас | Вимір і опис | Представник | Підтверджена комбінація / результат | Кейси |
|---|---|---|---|---|
| EP-U1 | Відомий стандартний користувач | `standard_user` | Коректний пароль → S | TC-AUTH-01 |
| EP-U2 | Заблокований користувач | `locked_out_user` | Коректний пароль → відмова через блокування | TC-AUTH-07 |
| EP-U3 | Невідоме непорожнє ім’я | `UNKNOWN_USERNAME` | `DEMO_PASSWORD` → невідповідність даних | TC-AUTH-06 |
| EP-U4 | Порожнє ім’я | `EMPTY` | Коректний або порожній пароль → Username required | TC-AUTH-02, TC-AUTH-03 |
| EP-P1 | Коректний пароль | `DEMO_PASSWORD` | Стандартний користувач → S; заблокований → відмова | TC-AUTH-01, TC-AUTH-07 |
| EP-P2 | Неправильний непорожній пароль | `WRONG_PASSWORD` | Стандартний користувач → невідповідність даних | TC-AUTH-05 |
| EP-P3 | Порожній пароль | `EMPTY` | Стандартний користувач → Password required; порожнє ім’я → Username required | TC-AUTH-02, TC-AUTH-04 |
| EP-S1 | Немає входу в новому контексті | Чистий контекст | Прямий каталог → F та помилка доступу | TC-AUTH-09 |
| EP-S2 | Є успішний вхід | Контекст після A | Reload → S | TC-AUTH-12 |
| EP-S3 | Виконано вихід | Контекст після A і Logout | Прямий каталог → відмова; повторний вхід → S | TC-AUTH-10, TC-AUTH-11 |

TC-AUTH-02 потрібний окремо: перевіряє пріоритет повідомлень, коли не заповнені обидва поля. TC-AUTH-03 ізолює порожній Username. TC-AUTH-05 і TC-AUTH-06 мають однаковий текст помилки, але покривають різні класи невірних даних. Неперевірений повний декартів добуток класів не включено.

## Тест-кейси

### TC-AUTH-01 — успішний вхід через Login

- **Requirement ID:** AUTH-01.
- **Тип / пріоритет / техніка:** позитивний / P0 / Equivalence Partitioning, переходи станів.
- **Передумови:** L.
- **Дані:** `standard_user`, `DEMO_PASSWORD` (EP-U1, EP-P1).
- **Кроки:** 1. Ввести Username. 2. Ввести Password. 3. Натиснути `Login`.
- **Очікуваний результат:** S.

### TC-AUTH-02 — обидва поля порожні

- **Requirement ID:** AUTH-02.
- **Тип / пріоритет / техніка:** негативний / P1 / Equivalence Partitioning, перевірка пріоритету валідації.
- **Передумови:** L.
- **Дані:** Username = `EMPTY`, Password = `EMPTY` (EP-U4, EP-P3).
- **Кроки:** 1. Не заповнювати поля. 2. Натиснути `Login`.
- **Очікуваний результат:** F; точна помилка `Epic sadface: Username is required`. Повідомлення стосується Username, а не Password.

### TC-AUTH-03 — порожнє ім’я за заповненого пароля

- **Requirement ID:** AUTH-02.
- **Тип / пріоритет / техніка:** негативний / P1 / Equivalence Partitioning.
- **Передумови:** L.
- **Дані:** Username = `EMPTY`, Password = `DEMO_PASSWORD` (EP-U4, EP-P1).
- **Кроки:** 1. Залишити Username порожнім. 2. Ввести Password. 3. Натиснути `Login`.
- **Очікуваний результат:** F; точна помилка `Epic sadface: Username is required`.

### TC-AUTH-04 — порожній пароль за заповненого імені

- **Requirement ID:** AUTH-03.
- **Тип / пріоритет / техніка:** негативний / P1 / Equivalence Partitioning.
- **Передумови:** L.
- **Дані:** Username = `standard_user`, Password = `EMPTY` (EP-U1, EP-P3).
- **Кроки:** 1. Ввести Username. 2. Залишити Password порожнім. 3. Натиснути `Login`.
- **Очікуваний результат:** F; точна помилка `Epic sadface: Password is required`.

### TC-AUTH-05 — неправильний пароль стандартного користувача

- **Requirement ID:** AUTH-04.
- **Тип / пріоритет / техніка:** негативний / P0 / Equivalence Partitioning.
- **Передумови:** L.
- **Дані:** `standard_user`, `WRONG_PASSWORD` (EP-U1, EP-P2).
- **Кроки:** 1. Ввести Username. 2. Ввести неправильний Password. 3. Натиснути `Login`.
- **Очікуваний результат:** F; точна помилка `Epic sadface: Username and password do not match any user in this service`.

### TC-AUTH-06 — невідомий користувач

- **Requirement ID:** AUTH-04.
- **Тип / пріоритет / техніка:** негативний / P0 / Equivalence Partitioning.
- **Передумови:** L.
- **Дані:** `UNKNOWN_USERNAME`, `DEMO_PASSWORD` (EP-U3, EP-P1).
- **Кроки:** 1. Ввести невідомий Username. 2. Ввести Password. 3. Натиснути `Login`.
- **Очікуваний результат:** F; точна помилка `Epic sadface: Username and password do not match any user in this service`. Збіг із TC-AUTH-05 визначено текстом очікування; виконання іншого кейсу не потрібне.

### TC-AUTH-07 — заблокований користувач із правильним паролем

- **Requirement ID:** AUTH-05.
- **Тип / пріоритет / техніка:** негативний / P0 / Equivalence Partitioning, тестування за ризиком.
- **Передумови:** L; використовується вже заблокований демоакаунт, створювати блокування невдалими спробами не потрібно.
- **Дані:** `locked_out_user`, `DEMO_PASSWORD` (EP-U2, EP-P1).
- **Кроки:** 1. Ввести Username. 2. Ввести Password. 3. Натиснути `Login`.
- **Очікуваний результат:** F; точна помилка `Epic sadface: Sorry, this user has been locked out.`

### TC-AUTH-08 — вихід до порожньої форми

- **Requirement ID:** AUTH-06.
- **Тип / пріоритет / техніка:** позитивний / P0 / переходи станів: вхід → вихід.
- **Передумови:** A у власному контексті.
- **Дані:** `standard_user`, `DEMO_PASSWORD` для підготовки.
- **Кроки:** 1. Натиснути `Open Menu`. 2. Натиснути `Logout`.
- **Очікуваний результат:** точний URL `LOGIN_URL`; форма входу видима; Username і Password порожні; повідомлення про помилку та список товарів не відображаються.

### TC-AUTH-09 — прямий каталог без попереднього входу

- **Requirement ID:** AUTH-07.
- **Тип / пріоритет / техніка:** негативний / P0 / Equivalence Partitioning, тестування за ризиком.
- **Передумови:** новий чистий контекст; не виконувати L або A, одразу відкрити цільовий URL.
- **Дані:** `INVENTORY_URL`, стан EP-S1.
- **Кроки:** 1. Відкрити `INVENTORY_URL` без входу.
- **Очікуваний результат:** F; точна помилка `Epic sadface: You can only access '/inventory.html' when you are logged in.`

### TC-AUTH-10 — прямий каталог після Logout

- **Requirement ID:** AUTH-07.
- **Тип / пріоритет / техніка:** негативний / P0 / переходи станів, Equivalence Partitioning.
- **Передумови:** A у власному контексті.
- **Дані:** `standard_user`, `DEMO_PASSWORD` для підготовки; `INVENTORY_URL`, стан EP-S3 після кроку 1.
- **Кроки:** 1. Відкрити `Open Menu`, натиснути `Logout`, переконатися в поверненні на `LOGIN_URL`. 2. У тій самій вкладці та контексті напряму відкрити `INVENTORY_URL`.
- **Очікуваний результат:** F; точна помилка `Epic sadface: You can only access '/inventory.html' when you are logged in.`

### TC-AUTH-11 — повторний вхід через Enter після виходу

- **Requirement ID:** AUTH-08.
- **Тип / пріоритет / техніка:** позитивний / P1 / переходи станів: вхід → вихід → повторний вхід.
- **Передумови:** A у власному контексті.
- **Дані:** `standard_user`, `DEMO_PASSWORD` для підготовки й повторного входу.
- **Кроки:** 1. Відкрити `Open Menu`, натиснути `Logout`, переконатися в поверненні до форми входу. 2. Ввести Username і Password. 3. З фокусом у Password натиснути Enter.
- **Очікуваний результат:** S після повторного входу. Очікування не поширюється на Enter з інших елементів форми.

### TC-AUTH-12 — оновлення каталогу після входу

- **Requirement ID:** AUTH-09.
- **Тип / пріоритет / техніка:** позитивний / P1 / переходи станів: вхід → reload → збережений доступ.
- **Передумови:** A у власному контексті.
- **Дані:** `standard_user`, `DEMO_PASSWORD` для підготовки; стан EP-S2.
- **Кроки:** 1. Виконати звичайне оновлення сторінки каталогу в тій самій вкладці та контексті.
- **Очікуваний результат:** S. Кейс не встановлює строку життя сесії й не перевіряє закриття браузера.

### TC-AUTH-13 — тип поля Password

- **Requirement ID:** AUTH-10.
- **Тип / пріоритет / техніка:** перевірка властивості UI / P1 / перевірка підтвердженої властивості.
- **Передумови:** L.
- **Дані:** поле `Password`; введення облікових даних не потрібне.
- **Кроки:** 1. Перевірити HTML-атрибут `type` поля Password через інспектор браузера.
- **Очікуваний результат:** `type="password"`. Це перевірка підтвердженої властивості поля, не доказ шифрування, безпечного зберігання або відсутності витоків пароля.

| Requirement ID | Підтверджена поведінка | Кейси з цільовою перевіркою | Покриття дизайном |
|---|---|---|---|
| AUTH-01 | Успішний стандартний вхід | TC-AUTH-01 | Так |
| AUTH-02 | Обов’язковий Username; пріоритет за двох порожніх полів | TC-AUTH-02, TC-AUTH-03 | Так, обидва варіанти |
| AUTH-03 | Обов’язковий Password | TC-AUTH-04 | Так |
| AUTH-04 | Спільна помилка для неправильного пароля та невідомого імені | TC-AUTH-05, TC-AUTH-06 | Так, обидва класи |
| AUTH-05 | Заборона входу заблокованому користувачу | TC-AUTH-07 | Так |
| AUTH-06 | Logout, порожня форма, відсутність помилки й каталогу | TC-AUTH-08 | Так |
| AUTH-07 | Заборона прямого каталогу без входу та після виходу | TC-AUTH-09, TC-AUTH-10 | Так, обидва стани |
| AUTH-08 | Повторний вхід після Logout; Enter у Password | TC-AUTH-11 | Так |
| AUTH-09 | Доступ зберігається після reload | TC-AUTH-12 | Так |
| AUTH-10 | Поле Password має тип password | TC-AUTH-13 | Так |

Усі 10 підтверджених пунктів мають цільові кейси. Вхід у передумовах інших кейсів не зараховується як окреме цільове покриття AUTH-01. Матриця не означає повного покриття всієї функціональності авторизації або захисту сервера.

## Відсутнє покриття та відкриті питання

Нижченаведене виключено з виконуваних кейсів, оскільки expected result не підтверджено:

| Прогалина | Потрібне уточнення |
|---|---|
| Регістр, початкові/кінцеві пробіли, рядки лише з пробілів | Чи є нормалізація та чутливість до регістру для кожного поля? |
| Довжина, Unicode, допустимі символи | Які документовані межі й правила? Без них Boundary Value Analysis не застосовано. Порожнє значення покрите як окремий клас EP. |
| Виправлення невдалого входу без reload, закриття помилки | Яка поведінка форми та повідомлення після редагування й повторного submit? |
| Спеціальні демоакаунти | Який контракт `problem_user`, `performance_glitch_user`, `error_user`, `visual_user`? |
| Інші захищені URL, Back/Forward | Які маршрути захищені та які точні результати навігації? |
| Простій, завершення браузера, інші вкладки/пристрої | Які строк дії сесії, правила відновлення та область дії Logout? |
| Повторні невдалі спроби | Чи є ліміт спроб, тимчасове блокування та розблокування? |
| Продуктивність, доступність, сумісність | Які SLA, критерії доступності та підтримувані браузери/пристрої? |
| Серверна авторизація та захист сесій | Які API, модель сесії й вимоги безпеки доступні для окремої перевірки? UI-кейси цього не доводять. |
| Статус вимог | Хто затверджує спостереження AUTH-01–AUTH-10 і точні тексти помилок як продуктовий контракт? |

Результати виконання та автоматизаційне покриття цього набору поки не визначені. Історичний результат запуску з попереднього плану не є результатом виконання цих 13 кейсів.
